# Подход к классификации намерений MedZvon

## Почему четыре этапа и именно в таком порядке

1. **Нормализация** — приводит текст к предсказуемому виду. Без этого fuzzy-match и словари работают нестабильно: регистр, пунктуация и лишние пробелы создают ложные несовпадения.

2. **Восстановление артефактов STT** — выполняется до скоринга, потому что типичные ошибки STT (разрывы слов, omonимы) имеют структурные паттерны. Проще один раз «починить» текст, чем дублировать правила в каждом intent.

3. **Скоринг** — отделяет «что совпало» от «насколько мы уверены». Weighted keyword matching даёт числовой score, который можно сравнивать между намерениями.

4. **Принятие решения** — отдельный этап для политики «не угадывать». Даже если скорер нашёл слабый сигнал, финальный шаг может вернуть UNCLEAR.

Порядок repair → filter stop words выбран специально: префиксы вроде «за» нужны для склейки «за писаться», но удаляются как заполнители только после repair.

## Почему rule-based + fuzzy, а не ML/embeddings

| Критерий | Rule-based + fuzzy | ML / LLM |
|----------|-------------------|----------|
| Детерминизм | Одинаковый вход → одинаковый выход | Зависит от модели |
| Скорость | Микросекунды на CPU | Сеть / GPU |
| Объяснимость | Видно, какое слово дало score | Чёрный ящик |
| Домен | 7 классов, ~50 ключевых слов | Избыточно |

Бриф явно требует кода, который работает *до* или *вместо* LLM — rule-based pipeline этому соответствует.

## Как сопоставляем текст с намерением

- **Точное совпадение** ключевого слова или фразы → полный вес из `intentPatterns.js`
- **Fuzzy match** (Levenshtein ≤ 2, слово ≥ 4 букв) → 70% веса. Покрывает «скока» ≈ «сколько», «прием» ≈ «приём»
- **Фразы** (2–3 слова) → бонусный вес, помогает disambiguation

Словари вынесены в `data/intentPatterns.js` — добавление нового синонима не требует изменения логики пайплайна.

## Что происходит при низкой уверенности

В коде это выглядит так:

```javascript
if (top.score === 0 || confidence < 0.35) {
  return { intent: Intent.UNCLEAR, confidence, reason: 'low_confidence' };
}
```

**UNCLEAR — валидный результат**, не ошибка. В реальной системе при UNCLEAR диалоговый менеджер задаёт уточняющий вопрос: «Не могли бы вы повторить, чем могу помочь?» — вместо того чтобы повести разговор в неверную ветку.

Дополнительные правила UNCLEAR:
- **gibberish** — шум, бессмысленные повторы гласных
- **farewell_without_intent** — «спасибо, до свидания» без запроса
- **ambiguous_intent** — два намерения с близким score (например, BOOK + INFO)
- **multiple_strong_intents** — два и более намерения с score ≥ 2.0 (составной запрос)

## Ограничения и развитие

**Ограничения текущего подхода:**
- Словари нужно пополнять вручную при новых формулировках
- Fuzzy match может давать ложные срабатывания на очень коротких словах (минимальная длина 4 символа снижает риск)
- Нет учёта контекста предыдущих реплик диалога

**При масштабировании добавили бы:**
- Конфигурируемые пороги confidence per intent
- A/B тестирование порогов на реальных логах STT
- Fallback на LLM только для UNCLEAR с confidence 0.2–0.35 (гибридный режим)
- Расширение homophone-словаря на основе частых ошибок конкретного STT-движка
